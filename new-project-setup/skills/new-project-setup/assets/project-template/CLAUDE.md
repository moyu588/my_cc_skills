## 第 0 条铁律（凌驾于一切之上）

- **任何时候，生产环境与数据的安全稳定，优先于进度和功能。**任何操作若可能触碰生产，立即停下、升级重型流、向用户确认。
- **生产禁区清单**：【填写：生产目录路径、生产容器/systemd 服务名、生产数据库位置、生产端口。示例：/srv/myapp 为生产目录，未经授权禁止任何写入/覆盖/构建；myapp.service 为生产服务，禁止随意 stop/restart】
- **禁止私自同步代码到生产**。生产同步必须经过：① 测试环境验证通过 → ② 用户明确确认 → ③ 才能执行。
- 禁止使用默认账号密码测试/验证；需要登录验证时向用户索取。禁止未经授权修改密码/凭据。

## 工作流规则

- **修改代码前必须 git status**：工作区不干净先 commit checkpoint 再开发；干净则直接开发。绝不跳过——失败时可 `git reset --hard` 干净回退。
- **先答复/先计划，确认后实施**：任何非平凡操作（修改代码、部署、批量文件操作）必须先给出计划，等用户明确确认后再动手。纯问答、只读查询不受此限。
- **6 条高危触发器（碰任何一条，强制从轻量流升级重型多代理流）**：
  1. 认证/授权/密码/用户敏感数据相关代码
  2. 数据库结构变更（加列/删列/迁移/ALTER/DROP）
  3. 生产环境部署/同步/发布
  4. 不可逆批量操作（批量删除、批量改库、批量覆盖文件）
  5. 外部 API 密钥、凭据的处理代码
  6. 架构级重构（跨多文件、改公共接口）

  重型流 = planner 出方案（用户确认）→ tdd-guide 先写测试 → 实现 → code-reviewer + security-reviewer + 语言 reviewer 三路并行评审 → CRITICAL 清零 → 用户点头才提交。
- **报错信息必须详细具体**：后端异常 `f"{type(e).__name__}: {str(e)}"`；前端展示 `e.response?.data?.detail || e.message`，不许吞错只报"操作失败"。
- **导入/批量写库逻辑必须整体包 try/except**：异常 rollback 后返回 500+详细信息。

## 数据库与环境陷阱

- **数据库**：【填写：类型、文件/服务位置、建表与迁移方式。示例：SQLite 无迁移文件；models.py 定义模型 + create_all() 重启自动建表，但只建不改——加列/删列必须手动 ALTER TABLE，改库前先 cp 备份 db 文件】
- **环境陷阱**：【填写：本机/本项目踩过的坑。示例：PowerShell 里 python -c 传多行代码双引号会被剥离，改用单引号或写临时 .py 文件】
- **测试服务规矩**：测试服务必须绑 `0.0.0.0` 的**非生产端口**（内网可访问才算交付）；生产端口收敛到 `127.0.0.1` 是安全要求。两者不可混淆。测试前无法确定某资源属于生产还是测试时，先停下问用户。

## 发布检查清单（每次发布逐项执行，不可跳过）

【按下面七步骨架填成本项目的具体命令】

1. **确认发布内容**：`git log --oneline <上次tag>..<默认分支>` 列出变更，按 backend/frontend/config 分类
2. **生产拉取**：`git pull origin <默认分支>`；报冲突先停下排查，禁止强制 checkout/覆盖
3. **前端有变更必须重新构建**（`npm run build` 或本项目命令）
4. **构建产物内容验证**：用 `grep` 搜产物中的特征字符串（新接口路径/新按钮文案），不能只 `ls` 证明文件存在
5. **后端有变更必须重启服务**：重启 → 确认 active → curl 验证 HTTP 200
6. **打 tag 标记发布**：`git tag vX.Y.Z && git push origin --tags`
7. **输出验证摘要表格**：pull 结果、构建验证、服务状态、HTTP 验证逐项列出

## Token 纪律

- 大文件（>300 行）先 `limit:100` 局部读再按需扩展；找符号/模式优先 Grep。
- 大范围代码探索交给子代理，主会话只收结论。
- 同一路径追 3 次没找到 bug 就加日志或问用户；工具调用失败不要用相同参数重试；先读清报错再动手。
